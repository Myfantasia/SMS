# SMS Orientation & Growth Roadmap

This repo has no root `README.md` or `CLAUDE.md` — this skill is the onboarding doc. Read it fully before making non-trivial changes; it's short by design.

## Hard rules (do not violate these)

1. **Never run `makemigrations` or `migrate`.** The user runs migrations themselves, always. If a model change needs a migration, say so and stop there — don't generate or apply it.
2. **Never hardcode department names.** `Department` (school/models/classSubjects_models.py:280) is a real, admin-editable DB model, not a fixed 6-item enum anymore. If you need department data, query it — don't reuse the old Languages/Mathematics/Sciences/Humanities/Technical/PE list from memory (see Known Gap #1 below for where that list still leaks in as a fallback).
3. **Before a broad NFR audit, ask which axis matters right now.** Standing priorities are performance, fault-tolerance, scalability, security, and maintainability — but "review the system" without a stated focus should get a clarifying question, not a five-axis audit nobody asked for.
4. **Heavy/big updates need a written plan and a saved artifact before implementation starts.** "Heavy/big" = anything spanning multiple files or components, introducing a new subsystem or capability (e.g. a theme-mode system, a new reusable UI component, a cross-cutting security fix), or any multi-step redesign — not a one-line fix or a single-file tweak. For these: (a) use plan mode / the `writing-plans` skill to produce a concrete implementation plan and get it confirmed before editing code, and (b) publish that plan as an Artifact (via the `Artifact` tool) so it lands in the user's own artifact collection, not just as chat text — this is how the user wants to review and keep a record of scope before the work happens. Small, obviously-scoped fixes don't need this ceremony; when unsure whether something counts as "heavy," lean toward planning first.
5. **The CBC curriculum dossier is a real file, just outside this repo.** `/home/jordan/Downloads/CBC-Kenya-Curriculum-Research (1).html` (~60KB, 850 lines) is the authoritative KICD/CBC-Kenya reference the user designated as the guide for how this SMS should model school entities — subjects, pathways, tracks, departments, grade bands. It is *not* checked into version control and does not live in the repo, so don't assume it's missing just because a repo-only search doesn't find it — read it directly when categorizing curriculum/subject/department structure, rather than guessing from code patterns or the partial reconstructions baked into `school/management/commands/backfill_departments.py`, `seed_preset_combinations.py`, and `seed_curriculum.py` (those three files encode *conclusions* drawn from the dossier, not the dossier itself, and the `Department` model's 9-department grouping is explicitly a practical staffing grouping, not an official KICD taxonomy). Note the `(1)` suffix and non-standard filename — a browser duplicate-download artifact, not a typo; confirm the path still resolves before relying on it, since a future re-download could rename it again.

## Architecture map

**One Django app, not many.** Everything backend lives under `school/` (a monolith), inside the `schoolmanagement/` project. Models are split by domain file under `school/models/` rather than one `models.py`:
- `models.py` — user-profile extensions (`TeacherExtra`/`StudentExtra`/`ParentExtra`/`AdminExtra`/`StaffExtra`), attendance, notices/events/notifications, academic year/exam term/grading/report summaries.
- `rbac_models.py` — custom `Permission`/`Role`/`UserRole` (see auth note below).
- `classSubjects_models.py` — the big one (28 models): curriculum, pathways, tracks, `Department`, `Subject`, quotas, allocations, exclusion/splitting rules.
- `timetable_models.py`, `assignments_models.py` (full quiz/rubric-grading subsystem), `chat_models.py`, `teachers_model.py`, `students_model.py`, `resultsModels.py`, `jobs_models.py`.

**Frontend is a separate SPA**: `frontend/` — React 19 + TS 5.9 + Vite 7 + Tailwind 4, pnpm-managed, react-router-dom v7. No Redux/Zustand/MobX, no React Query/SWR — state is plain hooks + a couple of Context providers (`ChatProvider`) and two socket hooks (`useChatSocket`, `useInboxSocket`). All API calls go through one shared axios instance (`frontend/src/libs/axiosInstance.ts`). Feature folders live under `frontend/src/components/` (academics, assignments, attendaces [sic], chats, curriculum, events, exams, Finance, leave, notices, results, subjectAllocations, timetable, plus `action routes/` and `lists pages/` for detail/list views). No frontend test suite exists at all.

**Two dev servers, loosely wired**: Django on `:8000` (Daphne/ASGI, needed for Channels), Vite on `:5173`. `vite.config.ts` has proxy rules for `/api`, `/static`, and `/ws`, but the actual frontend code (axios instance + both websocket hooks) hardcodes `localhost:8000` directly instead of using the proxy — a deliberate-but-fragile convention documented in comments in those files.

**Realtime = Django Channels, not Socket.IO.** Raw browser `WebSocket`, `channels_redis` for cross-process fan-out (`school/routing.py`, `school/consumers/chat_consumer.py`, `inbox_consumer.py`). Chat has per-thread groups plus a personal `inbox_{user_id}` group for sidebar updates. Both frontend socket hooks hand-roll exponential-backoff reconnect with a `generationRef` guard against stale-closure "zombie reconnects" — this was a real bug fixed recently, so don't simplify that guard away without understanding why it's there.

**Background jobs = Celery, dedicated `bulk_ops` queue, concurrency=1 on purpose** (correctness, not just throughput — these tasks mutate overlapping timetable/allocation/result data). Timetable generation, bulk allocation, and bulk result generation all *require* a running worker; without one, those endpoints return 503 forever (`school/jobs.py:is_worker_available`). If you're debugging a "stuck" bulk operation, check the worker first.

**Config-driven quota logic**: `SubjectQuota`/`QuotaDefaultRule` follow a "DB-first, hardcoded-ladder-as-last-resort" pattern (same pattern `GradingRule` uses). This is the pattern to follow for future config-driven features — prefer a DB rule table with an explicit, documented fallback over a fresh hardcoded ladder.

**Auth**: recently hardened — login throttling (`school/views/auth_rate_limit.py`, per-identifier and per-IP caps via Redis cache), verification-code expiry, and a `PRODUCTION_SECURITY` env flag gating HSTS/secure-cookie settings (off by default for local dev). Two authorization systems currently coexist: legacy `django.contrib.auth` Group-name checks (`school/decorators.py`) and a newer custom RBAC (`school/rbac.py` + `rbac_models.py`, Redis-cached). Know which one a given view uses before changing permission behavior — check for both `@require_permission` (RBAC) and Group-based decorators.

**Firebase is fully removed** (frontend and backend). If you see references to Firebase anywhere, it's leftover dead bytecode/cache, not active code — don't try to "restore" it.

## Modular monolith migration — in progress (started 2026-08-01)

The single `school/` app is being split into 14 Django apps (`apps/core`, `identity`, `academics`, `students`, `staff`, `allocations`, `attendance`, `assignments`, `messaging`, `finance`, `timetable`, `exams`, `results`, `analytics`), each with a `services.py`/DTO public boundary, enforced by `.importlinter`. Full plan (dependency graph, rationale for every deviation from the original spec, migration-safety mechanics, phased execution order): `/home/jordan/.claude/plans/wiggly-honking-honey.md` — **read its "Progress log" section first** before assuming what's done; it's kept current.

Quick orientation if you land here mid-migration:
- `apps/` holds the 14 new apps (scaffolded, registered in `INSTALLED_APPS`, each with a real `services.py`) — but as of this writing, the actual model classes still physically live in `school/models/*.py`. Each app's `services.py` queries `school.models.*` internally; that's intentional (Track A), not a bug.
- `finance` and `analytics` are one step ahead of the other 12: their view classes have been physically relocated from `school/views/{finance_views.py (deleted),results_views.py}` into `apps/{finance,analytics}/views.py`, with real `urls.py` included from the root urlconf. Same "no models exist for these two yet" reason they were picked as the Track B pilot — this was a code/routing move, not a migration.
- `core` is one step further still: `BackgroundJob`/`SystemAuditLog` are now physically defined in `apps/core/models.py` (deleted from `school/models/{jobs_models.py (file deleted entirely),classSubjects_models.py}`), migration `0092` applied.
- `messaging` too: `Notice`/`Event`/`Notification`/`ChatUserProfile`/`ChatThread`/`ThreadParticipant`/`MessageAudit`/`ChatActionResponse` are now physically defined in `apps/messaging/models.py` (deleted from `school/models/{models.py,chat_models.py (file deleted entirely)}`), migration `0093` applied. Note `ChatThread.related_student` still FKs to `school.models.models.StudentExtra` (identity hasn't relocated yet — that's the last Track B step).
- `attendance`+`assignments` too: `AttendanceSession`/`AttendanceRecord` now in `apps/attendance/models.py`, and all 9 assignments models (`Assignment`, `Question`, `StudentSubmission`, etc.) now in `apps/assignments/models.py` (deleted from `school/models/assignments_models.py`, file deleted entirely), migration `0094` applied. If you're touching the 4 `Assignment`/`AssignmentGroup`/`StudentAnswer` `ManyToManyField`s, note their join-table names are pinned via `db_table=` on the field itself — don't remove that kwarg, it's what keeps those join tables from silently renaming.
- `students`+`staff` too: `StudentTask`/`StudentPathwaySelection`/`StudentSubjectEnrollment` now in `apps/students/models.py`, and `TeacherLeave`/`LongTermReliefAssignment`/`TeacherStructuralAvailability` now in `apps/staff/models.py` (deleted from `school/models/{students_model.py,teachers_model.py}`, both files deleted entirely, plus 2 classes trimmed out of `classSubjects_models.py`), migration `0095` applied. Watch for bare-string FK references (`models.ForeignKey('SomeModel', ...)`) when relocating any model — they resolve within the *referencing model's own app*, so a bare string silently breaks the moment the model changes apps; always convert to a real import when relocating.
- `allocations`+`timetable` too (the highest-risk pair): all 7 allocations models (`SubjectQuota`, `SubjectAllocation`, `GlobalAllocationPolicy`, etc.) now in `apps/allocations/models.py`, all 4 timetable models (`Timetable`, `LessonAllocation`, etc.) now in `apps/timetable/models.py` (`TimeSlot` stays in `school.models.timetable_models`, academics-owned, not relocated yet) — with a hand-written no-op `SeparateDatabaseAndState` migration set (`apps/allocations/migrations/0001_initial.py`, `apps/timetable/migrations/0001_initial.py`, `school/migrations/0096_move_allocations_timetable_models_to_apps.py`), applied. Also: `.importlinter`'s 13 per-app "no cross-app model import" contracts now have `allow_indirect_imports = True` — without it, ANY cross-app `services.py`-to-`services.py` call breaks the contract (import-linter's `forbidden` type checks transitive chains by default), which very nearly blocked the first legitimate cross-service call (`apps.analytics.views` → `apps.allocations.services`) this repo has ever made. If a future contract edit removes that flag, expect every cross-app services call to break the build.
- **`orchestration/tasks.py` now exists and is live** — `school/tasks.py` is gone. `apps/allocations/services.py` gained real `rollover_allocations(...)`/`bulk_auto_allocate(...)` functions (the actual block-cloning/validator/contract-writing business logic, extracted from what used to be inline in the Celery tasks) and a new `AllocationValidationError` exception; `apps/timetable/services.py` gained `get_timetable_name(...)`. `orchestration/tasks.py`'s `rollover_allocations_task`/`bulk_auto_allocate_task` are the concrete composition-root pattern in action: each calls one `apps.allocations.services` function, then `apps.timetable.services.get_active_timetable_id`/`sync_with_allocation_changes`, then `apps.core.services.write_audit_log`, inside one `transaction.atomic()` block. Job completion notifications now go through the event bus (`BackgroundJobCompletedEvent` → `apps.messaging.receivers.handle_background_job_completed`) instead of a direct `Notification` import. `schoolmanagement/celery.py` has an explicit `app.autodiscover_tasks(['orchestration'])` (needed because `orchestration` isn't in `INSTALLED_APPS`, so default autodiscovery misses it) and `CELERY_TASK_ROUTES` points at `orchestration.tasks.*`. Anything importing `from school.tasks import ...` is now stale — use `orchestration.tasks` instead.
- `exams`+`results` too: 5 exams models (`ExamEvent`, `GradingRule`, `ExamResult`, `StudentReportSummary`, `ClassExamStatus`) now in `apps/exams/models.py`, 3 results models (`SubjectTermResult`, `StudentTermResult`, `ClassPerformanceAnalytics`) now in `apps/results/models.py` (`school/models/resultsModels.py` deleted entirely) — with a hand-written no-op `SeparateDatabaseAndState` migration set (`apps/exams/migrations/0001_initial.py`, `apps/results/migrations/0001_initial.py`, `school/migrations/0097_move_exams_results_models_to_apps.py`) — verified via `sqlmigrate` printing zero SQL, but **not yet applied**; check `showmigrations exams results school` for `0097`'s `[ ]`/`[X]` status. Admin registrations for the 5 exams models moved from `school/admin.py` to `apps/exams/admin.py` alongside their models. **Important**: `apps/analytics/views.py`'s 4 view classes still query `apps.exams.models`/`apps.results.models` directly (deep aggregate queries, not simple lookups) — this was already known tech debt from Track B step 1, now given a documented `.importlinter` `ignore_imports` exception (`apps.analytics.views -> apps.exams.models`/`-> apps.results.models`) rather than forced into a rewrite; a real DTO-based analytics rewrite is its own future project (the plan's "first true extraction candidate"), don't casually remove that exception without doing that rewrite first.
- **`academics` too (the biggest single relocation in the whole plan)**: all 18 models (`Curriculum`, `Pathway`, `Track`, `PresetCombination`, `Tier`, `GradeLevel`, `ClassStream`, `Department`, `Subject`, `SubjectCurriculumProfile`, `SubjectSelectionRule`, `SubjectCategoryLimit`, `SubjectExclusionRule`, `CurriculumPreset`, `SubjectPool`, `AcademicYear`, `ExamTerm`, `TimeSlot`) now in `apps/academics/models.py` — `school/models/classSubjects_models.py` and `school/models/timetable_models.py` are both deleted entirely. **Not yet applied** — check `showmigrations academics allocations assignments attendance exams results staff students timetable school` for the `[ ]`/`[X]` status of `academics 0001`, each dependent app's `0002_alter_*`, and `school 0098`. Only `identity` (auth.User extensions, RBAC) is left un-relocated — it's the deliberately-last Track B step.
- **Design pattern worth knowing before touching any `apps/*/models.py` FK field**: because 8 other apps already had FK fields pointing at academics-owned classes before academics itself relocated, this step established the convention of using **app-label-qualified string references** (`models.ForeignKey('academics.ClassStream', ...)`) instead of a Python import, whenever a model in one app needs a plain FK to a model in another app. Django resolves these through its app registry, not an import, so it never counts as a cross-app model import under `.importlinter` — no `ignore_imports` exception needed for a bare FK declaration. Reserve `ignore_imports` for genuine `services.py`-level business logic that needs a real model instance (see `apps.allocations.services`/`apps.timetable.services`/`apps.results.services`'s exceptions in `.importlinter` for examples) — don't reach for the string-reference trick there, since those callers already need the real ORM object, not just a resolvable relation.
- Relocating a model that other apps *already have applied migrations referencing* has a cost beyond the usual `school`↔`newapp` pair: every dependent app's own migration state has the old `to='school.<model>'` baked into historical `CreateModel`/`AddField` operations, and moving the model requires a paired `AlterField` migration in **each** of those apps updating `to=` to the new app label (zero SQL — `Meta.db_table` keeps the physical table identical). Don't try to guess these by hand — run `manage.py makemigrations <new_app> --dry-run -v3` in isolation; it computes the *entire* cross-app ripple in one pass and prints every affected app's exact migration content, which is what actually happened for `academics` (8 dependent apps' `0002_alter_*` migrations, `10` hand-written files total for that one step).
- `shared/events/` is the event bus (Django signals under the hood). `orchestration/` is the composition-root package for cross-app sagas — `orchestration/tasks.py` is its first (and so far only) real inhabitant.
- Before adding a new cross-domain call anywhere in `school/views/`, check whether an `apps.<domain>.services` function already covers it — don't add a fresh direct `school.models` cross-import if the services layer already has (or should have) the read/write you need.
- `.importlinter` only governs the `apps`/`orchestration` packages — it does not (and can't yet) check `school/` itself, so `school/` files freely importing `apps.*.services` is expected and fine (that's the intended direction during the transition).
- Never run `makemigrations`/`migrate` for this work either (see Hard Rule #1) — the plan's migration-safety section explains exactly what's safe to prepare vs. what's left for you to run.

## Growth roadmap (living — update this section as items resolve or new ones surface)

Each item is tagged by the NFR axis it belongs to, matching the user's standing priorities. When asked to work on a specific axis, start here.

**Security**
- Two parallel authz systems (Group-based vs RBAC) — not yet consolidated, though both are being relocated together into `apps/identity` as part of the modular monolith migration (see above), which sets up consolidation without forcing it in this pass.
- Hardcoded `localhost` assumptions in CORS/CSRF origins (`schoolmanagement/settings.py`), axios `baseURL`, and both WS hook base URLs — a real blocker before any non-local deployment.
- Multi-tenant isolation model decided 2026-08-11, not yet built: shared database, row-level `school` scoping per tenant-scoped model, with Postgres Row-Level Security (RLS) as a DB-enforced backstop — not schema-per-tenant, not database-per-tenant. `school_id` must always be server-derived from the authenticated user's session, never trusted from client input (the concrete IDOR risk here). See Scalability/Performance below for the rollout plan.

**Fault-tolerance**
- Celery is a hard, unguarded dependency for timetable/allocation/results generation — no health-check surfaced in the UI, so a dead worker just looks like a hang. A visible worker-status indicator would help a lot here.
- `QuotaDefaultRule`'s fallback ladder only covers exactly 6 legacy department names (hardcoded in `views_timetable.py`); renaming or adding departments beyond those 6 silently zeroes out quotas until someone manually adds a rule row. Self-documented in the `Department` model's docstring — a good candidate for a UI warning when a department has no matching rule.

**Maintainability**
- **New/reworked admin-dashboard UI now uses MUI (@mui/material), not raw Tailwind utility classes** — a 2026-08-11 decision, starting with `AssignSubjectsPage.tsx`. MUI previously existed only in `frontend/src/public/` (marketing/auth); the admin dashboard was 100% hand-rolled Tailwind with no shared Card/Button/Badge primitives. Prefer MUI components for any admin page you create or substantially rework going forward, themed via `frontend/src/layouts/theme/adminTheme.ts` (dashboard's blue/slate palette, not the public site's gold/terracotta) wired through `DashboardLayouts.tsx`. This is a "new work uses MUI" convention, not a retrofit mandate — expect both styles to coexist for a long transitional period. `@mui/icons-material` is NOT installed — keep using `lucide-react` for icons even inside MUI components (works fine via `startIcon`/`icon` props).
- No frontend test coverage at all, versus 21 backend test files (~2.4k LOC) concentrated on auth/signup/RBAC/results/electives/chat. The timetable engine and assignment/quiz grading flows are among the most complex frontend surfaces and currently have zero safety net.
- Frontend naming is inconsistent: folder names with spaces (`action routes`, `lists pages`), mixed casing (`Finance/` vs `attendaces/` [typo, kept as-is intentionally — don't "fix" it without checking for references] vs `chats/`), and a `common/` folder that only holds 3 files while several genuinely shared components (`Menu.tsx`, `Navbar.tsx`, `Notifications.tsx`, etc.) sit loose at `components/` root.
- Dead artifacts worth a cleanup pass: stale Firebase `.pyc` files, two backend test files deleted from source but still present as compiled bytecode, and some `__pycache__` files still tracked in git despite `.gitignore` now excluding them.
- `school/utils.py` (56KB) is a large grab-bag module — a refactor candidate once there's time to split it by concern.

**Scalability / Performance**
- **Multi-tenancy rollout (planned, entity-by-entity, decided 2026-08-11).** The system is single-school today (`identity.School` exists but is deliberately unwired — see model docstring). Growth plan is shared-DB + row-level scoping (see Security above), rolled out one entity at a time rather than all at once. First target: Curriculum Hub's `CurriculumPreset`/`SubjectPool` (each school's own free-form config) — `Curriculum`/`Pathway`/`Track`/`PresetCombination` stay unscoped/universal since they're national-curriculum structures shared by every school, not per-school config. `CurriculumPreset.name`'s current global `unique=True` will need to become `unique_together = ('school', 'name')` once scoping lands — a concrete pattern to repeat for any other model with a bare `unique=True` on a school-configurable field.
- **Second multi-tenancy target: Grade 9→10 (KJSEA) cross-institution promotion (flagged 2026-08-12, see `docs/superpowers/specs/2026-08-12-sss-core-math-and-promotion-design.md`).** JSS and Senior School are administratively separate institutions even when co-located, so a single school's admin has no authority to move a student's `cl` into another school's roster — today this transition just marks the student `'Graduated'` with a free-text `NationalExamRecord.destination` (placement school, admin-entered). Once multi-school data exists, `destination` becomes a real FK to another tenant's school record and actual cross-tenant roster placement becomes possible — not buildable before then.
- **Indexing for scoped tables**: once a model gets a `school` FK, its indexes must lead with `school_id` (e.g. `(school_id, display_order)` on `CurriculumPreset`), not just index the FK alone — this keeps one school's queries cheap regardless of how many rows other schools have in the same table. Postgres declarative partitioning by `school_id` is a later lever for tables that actually grow large under real multi-school load — premature with one tenant in the system, don't build it preemptively.
- **Cross-school concurrency** (many schools hitting the system at once): Postgres MVCC already isolates transactions row-by-row, so schools don't contend with each other by default — this is standard DB concurrency, not a special multi-tenancy problem. What actually needs building as schools multiply: connection pooling (pgbouncer) so stateless Django/Channels workers don't exhaust Postgres's connection limit, and horizontal scaling of app servers behind a load balancer. Read replicas are a lever for read-heavy endpoints once read load actually justifies it, not needed now.
- **Within-school concurrency** (multiple users of the *same* school racing on the *same* row — e.g. two teachers editing one student's marks at once): this is a different problem than tenant isolation and MVCC alone doesn't solve it. Needs explicit handling per case — `select_for_update()` inside a transaction for short critical sections, or optimistic concurrency (an `updated_at`/version check on save that rejects stale writes) for longer-lived edits. Also relevant once `school` scoping lands: audit `chat_consumer.py`/`inbox_consumer.py` Channels group naming to confirm a chat/inbox group can never accidentally span two schools.
- **Open architecture question, not yet resolved**: whether each of the 14 modular-monolith apps (see migration section above) stays one shared deployment serving every school (row-scoped data, one fleet of app servers — the recommended default, far lower ops cost) versus physically separate deployed instances per school per entity (true per-tenant microservices — an N-schools × 14-apps deployment matrix, generally only justified as a dedicated-instance tier for one specific customer, not the default for every school). Confirm which before building any tenant-provisioning infrastructure.

**Not yet a roadmap item, just a gap**: root `README.md` and `frontend/README.md` (currently generic Vite boilerplate) don't describe this project at all. Low-risk, high-value to fix whenever convenient.
