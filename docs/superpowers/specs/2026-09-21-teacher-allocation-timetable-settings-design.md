# Teacher Allocation, Timetable Connectivity, Substitution & Institution Settings — Design

Date: 2026-09-21
Status: Draft for review (architectural; one spec, six independently shippable phases)

## 1. Goal

Make teacher allocation accurate (no contradictory states), both automatic and manual, driven by
configuration stored as data, and tightly connected to the timetable. Add a proactive substitution
workflow, an Institution Settings hub, a stronger Subject Block Builder, and a site-wide Audit Log.

## 3. Cross-cutting conventions (apply to every phase)

1. **Config as data**: DB-first rule row, documented hardcoded fallback only as last resort (existing
   `GradingRule`/`QuotaDefaultRule` convention). No new hardcoded ladders.
2. **Every new or materially changed model gets a Django admin registration** in its owning app's
   `admin.py` (super-admin dashboard, Unfold-native per existing convention) alongside its React UI.
3. **Migrations are never run or generated by Claude.** Each phase lists the model changes; the user
   runs `makemigrations`/`migrate`. Tests that need new fields are written but flagged as blocked until migrated.
4. **Boundaries**: new logic goes through `services.py` DTOs; cross-app composition only in
   `orchestration/`. String app-label FK references, no cross-app model imports (import-linter stays green).
5. **Explainability**: any automated decision or violation carries a short human-readable reason.
6. New admin UI uses MUI per the 2026-08-11 convention; icons stay `lucide-react`.
7. UI changes cover their full reachable surface (no half-applied redesigns).

## 4. Phase 1 — Accuracy & consistency foundation

Problem: `AllocationValidator` gates rollover/bulk-allocate only; manual matrix save and other paths can
create states the automated paths would refuse.

- **One validator, every mutation path**: manual Matrix save, auto-draft, bulk-allocate, rollover, and
  rebalance all call the same validator. Result is a list of `BlockerDTO`
  (`code`, `severity` HARD|SOFT, `teacher_id`/`classroom_id`/`subject_id`, `message`, `rule_ref`, `suggested_fix`).
  `GlobalAllocationPolicy.enforcement_mode` decides whether SOFT blockers reject or warn.
- **Concurrency-safe writes**: bulk mutations run in `transaction.atomic()` with `select_for_update()` on
  in-scope `SubjectAllocation` and `AllocationPublishState` rows.
- **Published scopes are never touched** by any path (existing `AllocationPublishState` contract preserved).
- **Qualification matching** in auto-draft/bulk-allocate: candidate set = teachers with the subject in
  `qualified_subjects` (same source of truth the substitute finder uses); score bonus for existing
  contract continuity. Teachers outside qualification are only used when policy allows, flagged SOFT.
- **Departments come from the database, per curriculum tier** (replaces the hardcoded name ladder):
  - `apps.academics.services.list_departments(curriculum_id, tier_id=None) -> DepartmentDTO[]` returns active
    `Department` rows of that curriculum; with a tier, only departments actually used in that tier (derived from
    `SubjectCurriculumProfile` rows for the tier via `get_effective_department`, plus tier-less profile rows). No schema
    change needed for the lookup. Endpoint `GET /api/academics/departments/?curriculum=&tier=`; every picker (quota
    settings, splitting engine, allocation filters, block builder chips, substitution) uses it, keyed off the selected
    grade's `curriculum` and `tier`.
  - `QuotaDefaultRule` gains a nullable `tier` FK (config as data) and `trim_priority` (0 = protected longest … 3 = cut
    first). Resolution order: (department, tier, blocked) → (department, grade_band fallback for grades with no tier)
    → (any-department, tier, blocked) → explicit "no matching rule" blocker. `grade_band` stays only as the legacy
    fallback. `unique_together` becomes (department, tier, grade_band, applies_when_blocked).
  - `api_auto_generate_quotas` stops matching literal department names (`TECHNICAL_LIKE_DEPARTMENTS`, the
    Languages/Sciences ladder, and the hardcoded `_priority_tier`); those figures are seeded as rule rows per existing
    department and tier (extending `backfill_departments`/`seed_curriculum` conventions, checked against the CBC
    dossier) and read from the DB. A department with no rule no longer silently yields 0 lessons: it raises a
    "no matching rule" blocker in the Quota settings UI and generation output.
- Tests: validator parity across all paths (same input → same verdict), concurrent-apply race test,
  published-scope refusal, qualification filtering, tier-scoped department lookup, rule resolution order.

### 4.1 Publish-gated timetable sync (behaviour change)

Today, saving the Matrix commits `SubjectAllocation` rows, syncs the timetable and marks the class published in one
request; rollover and bulk-allocate also sync immediately inside `orchestration/tasks.py`. New model:

- **Draft**: manual saves, auto-draft, bulk-allocate, rollover and Rebalance apply only write `SubjectAllocation`
  rows. They never touch the timetable and never set published. Every save still runs the shared validator so
  contradictions are caught early, but as draft-stage warnings/errors.
- **Review**: the admin reviews the draft (per class, grade or whole scope), makes manual changes, and can re-run
  Rebalance any number of times.
- **Publish** is the only action that syncs the timetable. `publish_allocations(scope, review_fingerprint)`:
  1. Runs the full validator over the **entire scope including cross-class effects** (teacher totals across all
     classes in the grade/term, concurrent block clashes, qualification, weekly/class-group caps, structural-availability
     capacity, quota gaps and overages, block members with no teacher, block quota mismatches, teachers double-booked).
  2. HARD blockers stop the publish and are listed with reasons and suggested fixes. SOFT findings require explicit
     acknowledgement when `GlobalAllocationPolicy.enforcement_mode` is SOFT, and are also HARD-stopped when STRICT.
  3. Staleness check: if the draft changed since the admin's review (fingerprint mismatch), publish is refused and the
     review is refreshed. No silent publish of unreviewed edits.
  4. Shows a **publish preview** (dry run of `sync_with_allocation_changes`): lessons that would be ejected, swapped
     or need regeneration, so the admin sees the timetable impact before confirming.
  5. On confirm, in one `transaction.atomic()` with `select_for_update()`: re-validate → set `AllocationPublishState`
     → `sync_with_allocation_changes` → audit log → `AllocationsPublishedEvent` (notifies affected teachers).
- The sync produces a **Draft timetable only**; students and teachers see nothing until the separate, gated
  Timetable Publish in §7.2.
- Prior triples for the sync come from the timetable's existing lesson rows for the scope (not an in-memory
  snapshot), so re-publishing after an unpublish diffs correctly.
- **Unpublish** re-opens a class for edits as today; the timetable keeps its lessons until the next publish.
- Timetable generation and the feasibility prediction (§7.1) read only **published** allocations; drafts are shown
  as "not yet published" and never silently scheduled.
- Verify during planning: every current caller that syncs at save time (`teacherAllocation_view.py` lines around
  339/387/409, `orchestration/tasks.py` rollover and bulk-allocate) is switched to draft-only, with tests proving no
  timetable rows change before publish.

## 5. Phase 2 — Rebalance engine

- `apps.allocations.services.propose_rebalance(scope, options) -> RebalanceProposalDTO` — **read-only**;
  returns moves (teacher swaps/reassignments), blockers found, each move with a `why` (rule + score delta),
  and a `scope_fingerprint` (hash of in-scope allocation ids + updated timestamps).
- One shared **scorer** used by auto-draft, bulk-allocate and rebalance: workload balance vs
  `GlobalAllocationPolicy` caps, quota fit, qualification, structural availability capacity
  (fatigue kept at structural level per decision; real slot data consulted only when a timetable exists),
  prep consolidation (`min_classes_per_subject`).
- **Confirm = staleness-checked apply to the draft**: `orchestration/tasks.py` `rebalance_allocations_task`
  re-computes the fingerprint; mismatch → refuse with a clear message (no silent overwrite). On match:
  validator → write draft `SubjectAllocation` rows → audit log, one transaction. Rebalance does **not** sync the
  timetable itself; per §4.1 only Publish does. Before publish, Rebalance reads real timetable slot data
  (read-only) to identify blockers, and its result feeds straight into the publish review. "Finalize" in the UI is
  the Publish action, which re-validates and then syncs.
- **Blocker fixing**: rebalance proposes fixes for each blocker it can resolve (e.g. over-cap teacher →
  move a class group to a qualified teacher with headroom); unresolvable blockers stay listed.
- **Dry-run / compare**: propose against 2+ scopes/option sets side by side; nothing persisted.
- **Notifications**: publish `AllocationRebalancedEvent` on the event bus; `apps.messaging.receivers`
  notifies affected teachers and the operator (reuses the `BackgroundJobCompletedEvent` pattern).
- **Relocate views**: move `teacherAllocation_view.py` views to `apps/allocations/views.py`; URL paths unchanged.
- **UI**: Blockers panel + "Rebalance" flow in `AllocationDashboard` (propose → diff review with reasons → confirm),
  Auto/Bulk buttons upgraded to run the same scorer and show blockers with fixes.
- **Manual allocation UX** (`MatrixTable`): per-teacher live workload meters (weekly lessons, class groups, prep
  consolidation) that update as cells change; per-cell inline validation using the shared validator so a bad manual
  pick is explained before save; teacher picker ranked by qualification + headroom with the reason shown; undo/redo
  of unsaved edits; a per-class completeness indicator (gaps vs quota); keyboard-friendly editing.
- **Motion**: per the standing "improve UI/UX = add animation" convention, use the animation library already used
  in the MUI dashboard for meter/diff/panel transitions; Django admin stays Unfold-native. Dependencies are installed by the user.

## 6. Phase 3 — Quota balancing

Problem: `api_auto_generate_quotas` only trims over-capacity; it never redistributes slack, and
double/remedial counts are flat hardcoded numbers not tied to the final total.

- **Growth pass** mirroring the trim tiers: when effective demand < budget, grant extra lessons to
  under-served subjects in priority order, capped by a per-subject ceiling (new nullable
  `max_total_lessons` on `SubjectCurriculumProfile`, and on `QuotaDefaultRule`), never exceeding
  `daytime_capacity * SAFETY_MARGIN`. Block members are grown together (a block costs the week once).
- **Doubles/remedials as ratios**: derive `double_lessons_required` and `remedial_lessons_required` from a
  configurable ratio per department/grade-band (new fields on `QuotaDefaultRule`) applied to the final
  `total_lessons`; always clamped so `2*doubles <= total` and remedials never exceed remedial capacity.
  Explicit `SubjectCurriculumProfile` values still win.
- Output includes a per-subject explanation (source: profile / rule / ladder; trimmed / grown by N).
- Tests: growth never breaches capacity, doubles/remedials invariants, block deduplication, override precedence.

## 7. Phase 4 — Time-of-day-aware timetable placement

- New `Subject.preferred_time_of_day` (`MORNING` | `AFTERNOON` | `EITHER`, default `EITHER`) plus a
  department default via a rule row (config as data). Time-of-day of a slot is derived from `TimeSlot.start_time`
  (remedial slots keep their existing `is_remedial` handling).
- `generate_lessons_for_scope` treats it as a **soft** score alongside existing constraints (collision,
  availability, fatigue, block sync). Never a hard block; infeasible grids still schedule everything.
- Spreads repeated subjects across the day to avoid same-period-every-day monotony.
- Manual timetable editing remains fully available; manual placement shows a non-blocking hint when it
  violates a time-of-day preference.

### 7.1 Pre-generation feasibility prediction

Before "Auto-generate timetable" runs, a read-only `predict_timetable_feasibility(scope)` service reports, per class
stream: total demand vs daytime/remedial capacity, teachers whose assigned lessons exceed their real free slots
(structural availability minus `timetable_capacity_buffer_percent`), block slots that cannot be satisfied
simultaneously (no free qualified teacher per member subject), double-period shortfalls, and likely collisions.
Each finding carries a reason and a suggested fix (e.g. "run Rebalance", "reduce quota"). The generate button shows
this summary first and can hand blockers straight to the Rebalance flow, so generation starts from an allocation
already known to be schedulable. Auto and manual timetable creation both stay available: admins can edit any
generated lesson, and manual edits re-run the same collision/availability/fatigue validation with explained warnings.

### 7.2 Two-stage lifecycle: allocation publish syncs a *draft* timetable; timetable has its own gated publish

Today `api_update_timetable_status` only refuses going live when allocation gaps exist (`compute_school_allocation_gaps`);
it does not check conflicts or the timetable rules. New lifecycle:

1. **Allocation Publish (§4.1)** syncs into the timetable as a **Draft** only. It never changes `Timetable.status`
   and never makes anything visible to students, parents or teachers.
2. **Timetable review**: the admin reviews the synced/generated grid, regenerates or edits lessons manually, and
   may lock placements. All edits re-run the collision/availability/fatigue validation with explained warnings.
3. **Timetable Publish** (`publish_timetable(timetable_id, review_fingerprint)`, replacing the inline gate in
   `api_update_timetable_status`) verifies, over the whole timetable:
   - **Hard conflicts**: teacher in two places in one slot; class with two lessons in a slot; a teacher scheduled in a
     structural-unavailability slot, or on approved leave/long-term relief where those apply; block members not
     placed in the same slot across the grade; lessons in global (break/assembly) slots; double periods not on
     adjacent valid slots; a lesson whose (class, subject, teacher) no longer matches a **published** allocation.
   - **Completeness**: every class has its full quota placed (doubles and remedials included) and no unscheduled
     basket items remain; allocation gaps as today.
   - **Timetable rules** from `TimetablePedagogyPolicy`: `max_consecutive_periods`, `max_daily_subject_frequency`,
     `min_subject_spacing_periods`, `heavy_day_threshold`, `prevent_consecutive_heavy_days`, plus the teacher
     weekly cap from `GlobalAllocationPolicy`; time-of-day preference violations are reported as info only.
   - Severity follows `TimetablePedagogyPolicy.enforcement_mode`: HARD conflicts always block; rule violations
     block under STRICT and need explicit acknowledgement under SOFT (acknowledgements are audit-logged).
   - **Staleness**: refused if the timetable changed since the reviewed fingerprint.
4. On success, one `transaction.atomic()`: re-verify → set `status='Published'` (and `is_active` when requested,
   still singleton) → audit log → `TimetablePublishedEvent` (notifies teachers, students and parents via messaging).
   The verification report (checks run, warnings acknowledged) is stored with the audit entry.
5. **After going live**, an allocation change is a new draft: publishing it re-syncs the timetable, which moves back
   to needing review and republish. A live timetable is never silently altered; the sync result is staged and
   the admin chooses when to republish. Substitution/DailyCover (§10) keeps working on the live timetable.

The publish report is a read-only `verify_timetable(timetable_id) -> VerificationReportDTO` service the UI also
calls continuously in the review screen, so the admin sees the same list that will gate publishing.

### 8.1 School Profile

Full institution details (legal name, short name, motto, type/level, registration/MoE code, address,
county/sub-county, contacts, email, website, principal name, founding year, logo upload with existing
`profile_pic_validator`-style validation). Stored on `identity.School`. This is the **identifier for future
multi-tenancy**; this project does **not** add `school_id` scoping to other models (separate roadmap item,
shared-DB + row scoping decided 2026-08-11). A single profile row is treated as the current institution; the
service exposes `get_school_profile()` DTO so later tenant resolution has one seam to change.
Logo served via existing media handling.

### 8.2 Academic Calendar (read-oriented)

Professional month/agenda calendar aggregating: `Notice`/`Event` (messaging), `AcademicYear`/`ExamTerm`
boundaries (academics), and `ExamEvent` + promotion/national-exam dates (exams/students). Read-only
aggregation through each app's `services.py` into a `CalendarEntryDTO` (`kind`, `title`, `start`, `end`,
`source_ref`, `color`); a single endpoint `GET /api/institution/calendar/?from=&to=`. Includes an "Add event"
shortcut that reuses the existing Event creation. Timetable/allocation milestones are explicitly out of scope.

## 9. Subject Block Builder v2

Current: flat CRUD form; grade-wide blocks; created only for the active year/term; no rollover; backend
already blocks duplicate membership in the same grade/term/year. Engines consume blocks through
`build_grade_subject_block_map` (quota effective demand, timetable slot sync, `AllocationValidator._is_shared_block`).

Improvements:

1. **Visual builder**: grade × term board; each block a card listing member subjects with department chips;
   drag subjects between blocks/unassigned pool; subjects already blocked elsewhere are visibly disabled with
   the owning block named (surfacing the existing server rule instead of failing on save).
2. **Live impact preview before save** (`POST /api/timetable/blocks/preview/`, read-only):
   - *Quota alignment*: members share one slot so their `total_lessons` should match; mismatches listed with
     one-click "align to X".
   - *Teacher feasibility*: each member subject needs its own qualified, free teacher in the same slot;
     shows per-subject qualified-teacher count and flags shortfalls (reuses qualification + capacity data).
   - *Group size*: enrollment per member vs `SubjectSplittingRule.max_class_size` (extra parallel groups needed).
   - *Period structure*: ALL_DOUBLE feasibility against remaining double capacity.
   - *Capacity effect*: change in the grade's effective weekly demand vs daytime capacity.
3. **Generate from pathways**: build blocks for a grade from `PresetCombination`/`CurriculumPreset`
   options (senior-school pathway electives) instead of by hand; result is a draft the admin edits.
4. **Term/year rollover and clone**: "Copy forward" duplicates blocks (and optionally aligned quotas) into the
   next term/year, skipping members no longer eligible and reporting what was skipped; "Clone" within a term.
   Runs as a Celery job through `orchestration/` only if large; otherwise a synchronous transaction.
5. **Timetable connectivity**: each block card shows scheduled status (placed / unplaced lessons) and a
   deep link to its slots in the timetable; editing a block that has generated lessons warns and offers
   "regenerate affected lessons"; per §4.1 the change reaches the timetable only through the Publish action.
6. **Move to `apps/allocations`/`apps/academics` services**: block reads/writes go through a
   `services.py` DTO surface (`list_blocks`, `preview_block`, `save_block`, `rollover_blocks`) instead of the
   view reaching into models; `api_manage_subject_blocks` becomes a thin adapter.
7. Admin.py: `SubjectBlock` registered with inline membership, filters by grade/term/year.

Open question to verify during planning: whether blocks should support per-stream scope (currently
grade-wide). Default: keep grade-wide (YAGNI).

## 10. Phase 6 — Ad-hoc substitution workflow

Problem: only permanent structural blocks and date-range approved leave feed substitution. A short-notice
one-lesson absence (e.g. principal at a BOM meeting) has no model, and cover is only found when someone opens
the Cover tab.

- **New model** `TeacherAdHocUnavailability` in `apps/staff` (next to `TeacherLeave`): `teacher`, `date`,
  `time_slot` (or a set of slots), `reason`, `status` (SUBMITTED, COVERED, NO_COVER_FOUND, CANCELLED),
  `submitted_at`, `submitted_by`. Unique on (teacher, date, time_slot).
- **Lead-time rule**: submission must be at least `substitution_notice_hours` (default 3) before
  `date + time_slot.start_time`; otherwise rejected with the cutoff time in the message. The value lives in an
  editable setting (Institution Settings › Substitution & Notice Rules; stored on `TimetablePedagogyPolicy`).
  Admins with an explicit permission may override for genuine emergencies (audit-logged).
- **Sixth exclusion layer**: `_get_substitution_busy_teacher_ids` also excludes teachers with an ad-hoc
  unavailability on that date/slot (via `apps.staff.services`, no new dependency edge).
- **Proactive search**: on a valid submission, a Celery job (queue `bulk_ops`) finds qualified, free candidates
  for every affected lesson (existing qualification + 6-layer matrix + fatigue warnings), ranks them, and
  either auto-creates `DailyCover` (setting `auto_assign_cover`, default off) or notifies admins with the
  ranked shortlist for one-click confirm. No candidate → status NO_COVER_FOUND and an urgent notification.
- Reuses `TeacherLeave` approval: approved leave continues to generate covers the same way; leave and ad-hoc
  requests appear together in one upgraded **Cover tab** (timeline by date, status chips, candidate list,
  lead-time countdown).
- Events: `CoverNeededEvent`, `CoverAssignedEvent` → messaging notifies teachers, admins, and the covering teacher.
- Admin.py: model registered with filters by date/status/teacher.

## 11. Audit Log menu item

Standalone top-level page over `core.SystemAuditLog` (already written by ~15+ call sites through
`write_audit_log`). New `apps.core.services.list_audit_logs(filters, page)` with filters: user, module,
action type, date range, free-text; server-side pagination, CSV export, and per-record detail. Replaces the
timetable-scoped viewing endpoint (closes the known open item). Read-only; access controlled by RBAC permission.
Admin.py: `SystemAuditLog` remains read-only in the super-admin dashboard.

## 12. Data-model change summary (for the user to migrate)

- `identity.School`: profile fields + logo.
- `staff`: `TeacherAdHocUnavailability`.
- `academics`: `Subject.preferred_time_of_day`; `SubjectCurriculumProfile.max_total_lessons`.
- `allocations`: `QuotaDefaultRule` nullable `tier` FK, `trim_priority`, ratio fields, `max_total_lessons` (new
  `unique_together`); time-of-day default rule row/model. `AllocationPublishState` semantics change (publish becomes the
  sole timetable-sync trigger); a review fingerprint is computed, not stored, unless planning finds a need.
- `timetable`: `TimetablePedagogyPolicy.substitution_notice_hours`, `auto_assign_cover`.
- No table moves; all new fields nullable or defaulted.

## 13. Sequencing and delivery

Phases ship independently in this order: 1 → 2 → 3 → 5 (hub shell + School Profile + Audit Log first, Calendar and
Blocks v2 next) → 6 → 4. Phase 6 depends on the notice setting from Phase 5. The implementation plan will be split
into one plan per phase (multiple PRs), each with its own migration request to the user. Regression bar: existing
backend suite (163+ tests) and `lint-imports` green after every phase.

## 14. Testing strategy

TDD per phase. Backend: service-level unit tests with DTOs, transaction/race tests for apply paths, validator
parity tests, calendar aggregation tests, lead-time boundary tests (exactly 3h, 2h59m). Frontend has no test suite
today; new components get at least component-level tests where the harness is added, otherwise a documented manual
verification checklist run in the browser before each phase is called done.

## 15. Out of scope

Multi-tenant `school_id` scoping; full timetable+allocation joint solver; generic JSON rule engine (revisit if rule
types multiply); microservice extraction; timetable/allocation milestones on the calendar; per-stream blocks.
